- (decision) Why: frontend prototype (src/api/client.js) currently mocks all backend behavior client-side; this spec covers the real backend replacing those mocks for the office-role debit-card servicing screen, at demo/prototype tier (stub adapters for external bank systems), not production banking -- a vision-to-realize + pain-to-solve combination
- (capability) CAP-1 client-identity: employee views client identity card (profile, badges/triggers, open-case summary) -- intent: office employee opens a client and sees who they are and what needs attention; success: given a clientId, the identity endpoint returns profile+badges+triggers+openCases matching the shape client.js's getClientCard already expects
- (capability) CAP-2 offers: employee views the client's top personalized offer -- intent: employee sees one relevant upsell/offer per client without asking the marketing team directly; success: given a clientId, offers endpoint returns the current top offer (title/text/moreCount) via its stub adapter to the external offer engine (AD-10)
- (capability) CAP-3 card-account (cards): employee views and switches between the client's cards, sees balance/status/account -- intent: employee picks which of the client's cards to work with and sees its current state; success: given clientId+productId, returns the card list with balances; switching activeCardId re-fetches card-scoped data
- (capability) CAP-4 card-account (documents): employee retrieves account statement/certificate documents for a card -- intent: employee gets the documents needed to answer a client request on the spot; success: given cardId, returns the document list (statement, balance cert, flow cert) matching mockData.documents shape
- (capability) CAP-5 card-issuance: employee requests card reissue/new card and views issuance history -- intent: employee can act on a client's request to reissue or newly issue a card, and see prior issuance history; success: given clientId+productId, returns current application + history; a reissue/new-card action creates a new application record
- (capability) CAP-6 operations: employee views a card's transaction history including failed-transfer alerts -- intent: employee investigates a client's recent operations, including SBP transfer failures; success: given cardId, returns operations rows + any failedAlert matching mockData.operations shape
- (capability) CAP-7 risk-blocks: employee views a card's block status across SFM/FSSP-arrest/antifraud -- intent: employee sees why a card is restricted without contacting three separate back-office systems; success: given cardId, returns whichever of sfm/arrest/af blocks are active, each via its own stub port (AD-10)
- (capability) CAP-8 cashback: employee views accumulated cashback and category rates for a card -- intent: employee answers cashback questions without a separate lookup; success: given cardId, returns accumulated total, category list, and active promo matching mockData.cashback shape
- (capability) CAP-9 notifications: employee views/toggles a card's notification channels and the client's primary contact method -- intent: employee adjusts how a client is notified and sees their current contact channel (OMT); success: given cardId, returns notification toggles + notificationMethod; a toggle action flips one channel's on/off state
- (capability) CAP-10 incident-case (mass incidents): employee sees mass incidents relevant to the client, ingested from the monitoring system as they happen -- intent: employee is proactively aware of systemic issues affecting this client without polling; success: incident-case-service consumes MassIncidentOpened/Updated/Closed Kafka events (AD-5, AD-11) and the mass-incidents list reflects them without any REST poll to the monitoring system; employee can attach a client to a mass incident
- (capability) CAP-11 incident-case (single incidents & complaints): employee creates a single incident or complaint for the client and views existing ones -- intent: employee opens a formal case when self-service can't resolve the client's issue; success: given clientId, create/list endpoints for single incidents and complaints match mockData shapes and client.js's createSingleIncident/createComplaint contract
- (constraint) Every capability's service boundary, data ownership, and inter-service rule is fixed by the adopted architecture spine (AD-1..AD-11) -- this spec does not restate them, downstream reads the spine directly
- (constraint) Must preserve the existing frontend's REST resource shape (src/api/client.js) so the frontend requires only a fetchJson body swap, not a rewrite (spine AD-8)
- (constraint) Demo/prototype scope only: no real integration with SFM, FSSP, antifraud, offer engine, or the monitoring system -- all behind stub adapters (spine AD-10); rules out any capability requiring real bank-system credentials or protocols this iteration
- (note) Non-goals: real SFM/FSSP/antifraud/offer-engine/monitoring integration protocols; production auth (OAuth2/OIDC/SSO -- demo uses a trusted-header stub per AD-7); multi-role support (KC/Chat roles -- Office only); production deployment/cloud/K8s/CI-CD; tablet-responsive frontend layout and the Granat 2.0 design-kit work (separate frontend track, out of this backend spec entirely)
- (decision) Success signal: docker-compose stack (Gateway + 9 services + Kafka + 9 Postgres) runs locally; the existing React frontend has its client.js fetchJson swapped to call the Gateway; every current screen (client card, all 6 product tabs, incidents section) renders from live backend responses instead of mockData.js; a simulated MassIncidentOpened event published to Kafka appears in the incidents screen without a page reload or REST poll
- (assumption) Assumed the frontend adopts the backend by pointing its single fetchJson base URL at the Gateway (AD-6), not by the backend adapting to the frontend's current per-function mock signatures beyond matching response shape
- (assumption) Assumed 'Office role only' scope (per spine Deferred) means this spec's success signal is scoped to the Office frontend shell only -- Voice/Chat role shells are out of scope for demonstrating success, not just out of scope to build
- (question) Open: the spine's error envelope AD (from ARCHITECTURE-SPINE.md consistency conventions) fixes the shape { error: { code, message, details? } } but not the actual 'code' vocabulary (e.g. NOT_FOUND, VALIDATION_ERROR, UPSTREAM_UNAVAILABLE) -- needs a decision before incident-case/risk-blocks stories can specify error-path behavior precisely
- (question) Open: AD-11 fixes the Kafka envelope and topic naming but not the actual 'data' payload fields for MassIncidentOpened/Updated/Closed -- needs a decision before CAP-10's stories can be written precisely (likely: theme, product, start date, affected count, matchesClient, status -- mirroring mockData.massIncidents -- but not yet confirmed as the wire contract)
