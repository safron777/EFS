# mts-client-card-office backend

## Почему

Фронтенд-прототип на React (`src/api/client.js`) сейчас имитирует всё поведение бэкенда на стороне клиента — `fetchJson` просто делает задержку и возвращает статичные данные из `mockData.js`. Эта спека описывает настоящий бэкенд, который заменит эти моки для экрана обслуживания дебетовых карт сотрудником офиса/лёгкой сети: идентификация клиента, карты, операции, риск-блокировки, кэшбэк, уведомления, оформление и работа с инцидентами/жалобами. Это **demo/прототип-уровень** бэкенда — вместо реальных банковских систем (СФМ, ФССП, антифрод, offer-движок, мониторинг) стоят stub-адаптеры — так можно построить и продемонстрировать полную DDD/микросервисную форму уже сейчас, не дожидаясь реальных контрактов интеграции с этими системами.

## Способности (Capabilities)

- **CAP-1** — Идентификация клиента
  - **intent:** Сотрудник офиса открывает клиента и видит, кто это и что требует внимания (профиль, бейджи, алерты/триггеры, сводка открытых обращений).
  - **success:** По `clientId` эндпоинт идентификации возвращает профиль + бейджи + триггеры + открытые обращения — в форме, которую уже ожидает `getClientCard` из `client.js`.

- **CAP-2** — Топ-предложение
  - **intent:** Сотрудник видит одно релевантное персональное предложение для клиента.
  - **success:** По `clientId` эндпоинт offers возвращает текущее топ-предложение (title/text/moreCount) через свой stub-адаптер к внешнему offer-движку.

- **CAP-3** — Карты и баланс
  - **intent:** Сотрудник выбирает, с какой картой клиента работать, и видит её текущее состояние.
  - **success:** По `clientId` + `productId` возвращается список карт с балансами/статусом; переключение активной карты подгружает card-scoped данные заново.

- **CAP-4** — Документы по счёту
  - **intent:** Сотрудник получает документы, нужные для ответа клиенту прямо сейчас.
  - **success:** По `cardId` возвращается список документов (выписка, справка об остатке, справка о движении), соответствующий `mockData.documents`.

- **CAP-5** — Оформление/перевыпуск карты
  - **intent:** Сотрудник обрабатывает запрос клиента на перевыпуск или новую карту и видит историю прежних заявок.
  - **success:** По `clientId` + `productId` возвращаются текущая заявка и история; действие перевыпуска/новой карты создаёт новую запись заявки.

- **CAP-6** — История операций
  - **intent:** Сотрудник расследует недавние операции клиента, включая неуспешные переводы по СБП.
  - **success:** По `cardId` возвращаются строки операций и алерт о неуспешном переводе (если есть), соответствующие `mockData.operations`.

- **CAP-7** — Риск-блокировки
  - **intent:** Сотрудник видит, почему карта ограничена, не обращаясь в три разные бэк-офисные системы отдельно.
  - **success:** По `cardId` возвращаются активные блокировки — СФМ / арест ФССП / антифрод, каждая через свой stub-порт.

- **CAP-8** — Кэшбэк
  - **intent:** Сотрудник отвечает на вопросы по кэшбэку без отдельного запроса.
  - **success:** По `cardId` возвращаются накопленная сумма, ставки по категориям и активная промо-акция, соответствующие `mockData.cashback`.

- **CAP-9** — Уведомления
  - **intent:** Сотрудник настраивает каналы уведомлений клиента и видит его текущий основной способ связи (ОМТ).
  - **success:** По `cardId` возвращаются тумблеры уведомлений и способ уведомления; действие тумблера переключает состояние одного канала.

- **CAP-10** — Массовые инциденты
  - **intent:** Сотрудник заранее знает о системных проблемах, затрагивающих этого клиента, без опроса.
  - **success:** `incident-case-service` потребляет Kafka-события `MassIncidentOpened`/`Updated`/`Closed`, и список массовых инцидентов отражает их без единого REST-опроса системы мониторинга; сотрудник может привязать клиента к массовому инциденту.

- **CAP-11** — Единичные инциденты и жалобы
  - **intent:** Сотрудник открывает формальный кейс, когда самообслуживание не решает проблему клиента.
  - **success:** По `clientId` эндпоинты создания/просмотра единичных инцидентов и жалоб соответствуют формам `mockData` и контракту `createSingleIncident`/`createComplaint` из `client.js`.

## Ограничения (Constraints)

- Границы сервисов, владение данными и правила межсервисного взаимодействия для каждой способности фиксированы принятым архитектурным спайном (AD-1..AD-11 в `ARCHITECTURE-SPINE.md`) — эта спека их не повторяет.
- Нужно сохранить существующую REST-форму фронтенда (`src/api/client.js`), чтобы фронтенду потребовалась только замена тела `fetchJson`, а не переписывание (AD-8 спайна).
- Только demo/прототип-уровень: никакой реальной интеграции с СФМ, ФССП, антифродом, offer-движком или системой мониторинга — все за stub-адаптерами (AD-10 спайна). Исключает любую способность, требующую реальных учётных данных или протоколов банковских систем на этой итерации.

## Не входит в объём (Non-goals)

- Реальные протоколы интеграции с СФМ, ФССП, антифродом, offer-движком или системой мониторинга.
- Полноценная аутентификация продакшен-уровня (OAuth2/OIDC через корпоративный SSO) — в demo используется stub-заголовок от Gateway (AD-7 спайна).
- Поддержка нескольких ролей (КЦ/Чат) — существует только роль «Офис».
- Продакшен-контур развёртывания (облачный провайдер, Kubernetes, CI/CD, продвижение по окружениям).
- Планшетная адаптивная вёрстка фронтенда и работа над дизайн-китом Granat 2.0 — отдельный фронтенд-трек, полностью вне этой backend-спеки.

## Сигнал успеха (Success signal)

Стек `docker-compose` (Gateway + 9 сервисов + Kafka + 9 инстансов PostgreSQL) запускается локально, и существующий React-фронтенд — с `fetchJson` из `client.js`, переключённым на вызовы Gateway, — отрисовывает каждый текущий экран (карточка клиента, все 6 вкладок продукта, раздел инцидентов) из живых ответов бэкенда вместо `mockData.js`. Смоделированное событие `MassIncidentOpened`, опубликованное в Kafka, появляется на экране инцидентов без перезагрузки страницы и без REST-опроса.

## Допущения (Assumptions)

- Предположено, что фронтенд подключается к бэкенду через единый base URL `fetchJson`, указывающий на Gateway (AD-6), а не через адаптацию бэкенда под текущие сигнатуры мок-функций фронтенда сверх соответствия форме ответа.
- Предположено, что объём «только роль Офис» (по Deferred-секции спайна) означает, что сигнал успеха этой спеки ограничен фронтенд-оболочкой «Офис» — оболочки ролей КЦ/Чат вне объёма и для демонстрации успеха, не только для реализации.

## Открытые вопросы (Open Questions)

- Решение по конверту ошибок в спайне фиксирует форму (`{ error: { code, message, details? } }`), но не словарь значений `code` (например `NOT_FOUND`, `VALIDATION_ERROR`, `UPSTREAM_UNAVAILABLE`). Нужно решить до того, как истории risk-blocks/incident-case смогут точно описать поведение при ошибках.
- AD-11 фиксирует конверт и именование топиков Kafka, но не сами поля `data` для `MassIncidentOpened`/`Updated`/`Closed`. Вероятно, зеркалит `mockData.massIncidents` (theme, product, start date, affected count, `matchesClient`, status), но это ещё не подтверждено как контракт на проводе — нужно до того, как истории CAP-10 можно будет написать точно.
