## Суть (Intent)

**Проблема:** Бэкенда для `mts-client-card-office` пока не существует — нет структуры репозитория, нет Gateway, негде локально запустить 9 запланированных микросервисов. Все остальные истории (CAP-1..11) нуждаются в месте, куда можно приземлиться.

**Подход:** Поднять Maven multi-module скелет в `backend/` внутри существующего репозитория `EFS` — по одному модулю на bounded context (согласно AD-1) плюс модуль Gateway — с hexagonal-раскладкой пакетов, `docker-compose.yml`, связывающим Gateway + 9 сервисов + Kafka + 9 инстансов Postgres, и ровно столько кода на сервис, чтобы доказать: стек запускается целиком (загружающееся Spring Boot приложение с health-эндпоинтом). Никакая бизнес-способность (CAP-1..11) здесь не реализуется.

## Границы и ограничения (Boundaries & Constraints)

**Всегда:**
- Ровно девять сервис-модулей, именно как в AD-1 (`client-identity`, `offers`, `card-account`, `card-issuance`, `operations`, `risk-blocks`, `cashback`, `notifications`, `incident-case`) плюс `gateway` — не больше и не меньше.
- Каждый сервис-модуль следует hexagonal-раскладке пакетов из раздела Design Paradigm спайна (`domain/`, `application/`, `adapters/in/web/`, `adapters/out/persistence/`; `adapters/out/external/` — для `risk-blocks` и `offers`; `adapters/in/messaging/` — для `incident-case`), даже если в этой истории они по большей части пусты.
- Gateway — единственный контейнер, публикующий порт на хост (AD-6); 9 сервисов и Postgres/Kafka доступны только внутри сети docker-compose.
- У каждого сервиса — свой собственный контейнер/база PostgreSQL, без общей схемы (AD-1).
- Maven Wrapper (`mvnw`) закоммичен, запинен на Maven 3.9.16 — для удобства правки на хосте (см. примечание про JDK ниже); не то, на чём проверяется сборка.
- Сборка и запуск происходят исключительно внутри Docker (multi-stage `Dockerfile`, `eclipse-temurin:25` для сборки и рантайма); версия JDK на хосте (сейчас 17) не должна совпадать и не апгрейдится в рамках этой истории — решение принято, чтобы не блокировать Историю 0 локальной сменой тулчейна.

**Никогда:**
- Никаких бизнес-эндпоинтов сверх health-check — CAP-1..11 идут отдельными историями.
- Никакого CI/CD или конфигурации облачного развёртывания (Deferred в спайне).
- Никакой реальной интеграции с СФМ/ФССП/антифродом/offer-движком/мониторингом — эти stub-адаптеры приходят вместе со своей историей-способностью.

## Заметки по реализации (Implementation Notes)

- **Имена директорий модулей несут суффикс `-service`** (`client-identity-service`, ...), чтобы точно соответствовать буквальному дереву из Structural Seed спайна; строка границ «модули точно как в AD-1» трактуется как фиксация *набора и идентичности* девяти bounded context'ов (без переименования/перестановки/добавления), а не буквальной строки папки.
- **Версия Spring Cloud Gateway:** ни одна линия релизов Spring Cloud ещё не таргетит Spring Boot 4.1.x (новейшая, `2025.1.3`, таргетит Boot `4.0.8` — проверено по Maven Central). Вместо импорта всего `spring-cloud-dependencies` BOM (что откатило бы каждый `spring-boot-starter-*` к 4.0.8), `gateway/pom.xml` запинивает только `spring-cloud-starter-gateway-server-webflux:5.0.3` напрямую, оставляя BOM Spring Boot 4.1.1 родителя главным. Проверено работающим целиком в Docker.
- **`spring-boot-maven-plugin` нуждается в явном `<executions>`** (`repackage`, привязанный к `package`) в `pluginManagement` родителя — этот проект пинит Spring Boot через импорт BOM, а не через наследование `spring-boot-starter-parent`, который обычно неявно подключает это исполнение. Без этого `package` молча производит тонкий jar без записи `Main-Class` в манифесте («no main manifest attribute» при старте контейнера) вместо исполняемого Spring Boot jar.
- **Образ PostgreSQL 18 изменил ожидаемую точку монтирования тома**: теперь он хочет, чтобы монтировалась *родительская* директория (`/var/lib/postgresql`), а не `/var/lib/postgresql/data` напрямую, чтобы раскладывать поддиректории для конкретной мажорной версии. Монтирование старого пути заставляет контейнер отказываться стартовать на чистом томе. Все 9 сервисов Postgres монтируют `<service>-pgdata:/var/lib/postgresql`.
- **Обработка ошибок Gateway при недоступном бэкенде**: по умолчанию сбой проксирования (остановленный контейнер бэкенда, не резолвящийся DNS внутри сети compose, отказ в соединении) проваливается в стандартный реактивный обработчик ошибок Spring Boot и выходит наружу как голая `500`, а без явного таймаута HTTP-клиента Reactor Netty может держать клиента в подвешенном состоянии намного дольше разумного (наблюдалось: 15+ секунд без единого байта в ответ, против остановленного контейнера). Это прямо нарушает замороженную I/O-матрицу («Целевой сервис недоступен -> 502/503, а не зависание»), поэтому `gateway/application.yml` задаёт явные `spring.cloud.gateway.server.webflux.httpclient.connect-timeout` (3000мс) и `.response-timeout` (5с), а `GatewayErrorHandlerConfiguration` регистрирует `ErrorWebExceptionHandler` с более высоким приоритетом (`@Order(-2)`, впереди стандартного обработчика Boot на `-1`). Он маппит в `502` с конвертом спайна `{ error: { code, message } }` только *сетевые* исключения (`ConnectException`, `UnknownHostException`, `TimeoutException`, тайм-ауты соединения/чтения/записи Netty, `PrematureCloseException` из Reactor Netty — определяются обходом цепочки причин); всё остальное уходит в `Mono.error(ex)`, так что баг роутинга/конфигурации по-прежнему проявляется как обычная `500`, а не маскируется под «целевой сервис не ответил». Покрыто тестом `GatewayErrorHandlerConfigurationTest` (`WebTestClient` + `@SpringBootTest(webEnvironment = RANDOM_PORT)`, добавляет один дополнительный маршрут через бин `RouteLocator`, указывающий на закрытый локальный порт). Проверено: остановка контейнера-бэкенда превращает зависание на 15+ секунд в `502` за ~75мс.
- **Kafka (KRaft, без ZooKeeper)** использует официальный образ `apache/kafka:4.3.1` с конфигурацией однонодового KRaft, взятой прямо из собственного примера образа (`docker/examples/docker-compose-files/single-node/plaintext` в исходниках `apache/kafka`), адаптированной так, чтобы не публиковать порт на хост (AD-6) и анонсировать себя как `kafka:9092` в сети compose. `KAFKA_LOG_DIRS` подкреплён именованным томом (`kafka-data`), смонтированным в `/home/appuser` (уже существующий домашний каталог непривилегированного пользователя образа, уже принадлежащий этому пользователю), а не напрямую в путь лог-директории под `/tmp` — свежий том, смонтированный прямо на `/tmp/kraft-combined-logs`, поднимается с владельцем root и без источника, откуда скопировать права, из-за чего брокер (работающий под uid 1000) не может в него писать. Проверено: создан топик, контейнер перезапущен, топик всё ещё в списке после рестарта.
- **Известная неэффективность, не исправленная в этой истории:** этап Docker-сборки каждого сервиса разрешает свои Maven-зависимости независимо (нет общего кеша `~/.m2`, смонтированного между 9+1 этапами сборки), поэтому полный `docker compose build` заново скачивает одни и те же jar-файлы Spring Boot/Hibernate/Tomcat для каждого модуля. Функционально корректно (все 10 образов собираются), просто медленнее, чем нужно; `--mount=type=cache,target=/root/.m2` на двух строках `RUN mvn ...` в каждом Dockerfile решило бы это, если время сборки станет проблемой.
- В этой песочнице наблюдались повторяющиеся временные сбои TLS/registry при сборке против Maven Central и Docker Hub (сбросы хендшейка, одна оборванная загрузка зависимости); все устранены простым повтором без изменения конфигурации, т.е. не вызваны ничем в этом каркасе.

## Заметки по дизайну (Design Notes)

Kafka работает в режиме KRaft (без контейнера ZooKeeper) — Kafka 4.x полностью убрал поддержку ZooKeeper, так что контейнер ZK не был бы даже опцией при запиненной версии 4.3.1. `incident-case-service` — единственный сервис с Kafka-консьюмером в объёме этой истории, но брокер всё равно поднимается здесь как общая инфраструктура, поскольку от него зависит каждая будущая история, затрагивающая события.
